01 / ONTOLOGY

An ontology is a shared mental model — for machines.

Think of an ontology as the vocabulary and grammar of your business, written in a form a computer can reason over.

When an underwriter says “a joisted-masonry building in a protected Class 4 town with a sprinkler system in a light manufacturing occupancy,” every word is loaded with meaning — and every word connects to other concepts. Construction class implies vulnerability to wind and fire. Protection class modifies that vulnerability. Occupancy shapes exposure. The underwriter’s brain holds this web of concepts.

An ontology makes that web explicit. It names the classes (Location, Building, Occupancy, Peril), the properties (TIV, year built, construction type), and the relationships (a Building hasProtection, is exposedTo Perils, isLocatedIn a CatZone).

Without an ontology, the LLM knows the words. With an ontology, the system knows the meaning.

Once the world is modeled this way, rules become composable and inheritable. A rule that applies to “all combustible-construction buildings” automatically applies to anything the ontology classifies as combustible — frame, heavy timber, ordinary. You don’t write the rule four times. You write it once, against the concept.

Most importantly, ontologies compose across domains. A location ontology plugs into a peril ontology plugs into a reinsurance ontology. The same structure that supports underwriting supports claims, portfolio management, and regulatory reporting.

Fig. 01 — Minimal Commercial Property Ontology
I.

Meaning, not matching

An LLM might see “frame construction” and “wood frame” as similar strings. An ontology knows they are the same concept, and knows that concept is classified as combustible under ISO CC-1.

II.

Rules follow concepts

A rule attached to Combustible Construction automatically applies to every subtype — without re-authoring. Your underwriting manual becomes a small, maintainable tree instead of a sprawling document.

III.

Cross-domain consistency

The same Location concept anchors underwriting, claims, portfolio, and reinsurance. One broker address resolves to one entity everywhere — the foundation of clean accumulation and PML analysis.

02 / DEEPER

What’s happening inside each system.

Inside an LLM

A submission comes in as text. The model tokenizes it and passes the tokens through dozens of transformer layers, each applying attention across the sequence. At each position, the model produces a probability distribution over its vocabulary and samples the next token.

There is no separate “reasoning step.” What looks like reasoning — chain-of-thought, for example — is the model generating text that resembles reasoning it has seen in training data. It often gets the answer right because that pattern is well-represented in the corpus. It sometimes gets it confidently wrong for the same reason.

The model has no persistent representation of your underwriting manual or your expiring policy’s subjectivities. Even if you paste them into context, the model’s attention to them is probabilistic; there is no guarantee subjectivity CP-OPS-04 will be matched against the COPE and MSDS evidence when it should be.

Inside RAG + LLM

The submission triggers a retrieval step first. The system embeds the query, searches a vector index over your documents, and pulls back the top-k most relevant passages. This is deterministic — the same query returns the same passages.

Those passages are injected into the prompt. Now the LLM generates with your actual guidelines visible in its context window. Citations in the output refer to retrieved passages, which is a real improvement: hallucinated facts are much rarer, and the model’s answers are grounded in your content.

But the generation step is still an LLM. It can misread a retrieved clause, paraphrase it incorrectly, or let its training-data priors override what the passage actually says. And retrieval only works on documents — not on live portfolio data, APIs, or structured operational systems.

Inside a Neurosymbolic System

The same six documents arrive as text. A neural extractor (often an LLM itself, constrained) parses them into structured facts keyed by document and field: COPE.Building_3.partition = new_coating_cell, MSDS.Location_B3.flash_point = {18, 21, 24, 27°C}, Application.operations_change = "none".

These facts are asserted into a knowledge graph built on an ontology — one that knows SOV.Building_3, COPE.Building_3, MSDS.Location_B3, and SprinklerCert.Building_3 are the same physical entity. A reasoner then evaluates every applicable rule. Subjectivity CP-OPS-04 is represented as executable logic: IF observed_operation ∈ {coating, dipping, ignitable_liquid} AND prior_notice = false THEN subjectivity_unmet.

The conclusion isn’t generated — it’s derived. Every derivation produces a proof: the fact, the rule, and the binding. That proof is what makes the output auditable, consistent, and defensible.

03 / DEMO

A renewal that summarized clean — and didn't reconcile.

Meridian Fabrication has been a renewal account for three years. The broker submits the same six documents the carrier always sees: application, statement of values, COPE inspection, MSDS list, sprinkler certificate, and the expiring policy's subjectivities. A RAG-augmented LLM reads each document, cites each one, and lands on a confident renew with moderate rate increase. The neurosymbolic system reads the same six documents — and reaches a different decision, because the breach is not in any document. It is between them.

What the LLM did not reconcile

Every document read accurately. Nothing read against anything else.

  • Building 3 in the SOV, COPE inspection, sprinkler cert, and MSDS list are the same location
  • The application's “no operations change” answer conflicts with the COPE finding of a new coating cell
  • The MSDS list of low-flash-point solvent coatings indicates ignitable-liquid operations
  • The sprinkler certificate confirms operational status, not design adequacy for the changed hazard
  • The expiring-policy subjectivity CP-OPS-04 is no longer satisfied

Remediation path

The decision is refer / hold, not decline. NSAI returns the broker a structured remediation path. Click any step to see what satisfactory evidence looks like.

  • Satisfactory evidence Broker letter on letterhead specifying coating types, daily and maximum-on-premises quantities of each ignitable liquid, storage configuration (cabinets, control area, segregated room), dispensing method, and operational hours.
  • Satisfactory evidence Amended application or signed acknowledgement of operations change effective date, with corrected answers to operations-change, coating-operation, and flammable-liquid questions.
  • Satisfactory evidence Engineering report addressing whether existing ESFR design remains adequate given the changed hazard. Report should specifically address commodity classification, special-hazard suppression needs, and any required design modifications.
  • Satisfactory evidence Documented confirmation of one of: (a) adequate existing suppression for the changed hazard, (b) required upgrades with installation schedule and contractor commitment, or (c) operational controls sufficient to compensate (e.g., reduced quantities, segregation, ventilation, approved electrical).
  • Satisfactory evidence Revised quote with updated Building 3 classification, applicable warranties and exclusions, rating reflective of actual hazard, and explicit subjectivities for any items not cured at bind. All prior subjectivities (CP-OPS-04 and successors) reissued.
