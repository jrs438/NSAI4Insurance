A Primer for Insurance Leaders

Thinking beyond the model.

01 / DEFINE

What neurosymbolic AI actually is.

Neurosymbolic AI is a hybrid architecture that combines the pattern recognition of neural networks with the logical rigor of symbolic reasoning.

Large language models are neural networks — statistical engines that learn from vast amounts of text. They are brilliant at reading unstructured documents, understanding intent, and producing fluent language. But they reason probabilistically, not logically. Two runs of the same question can produce two different answers, and the model cannot show its work in a way a regulator would accept.

Symbolic AI is the older tradition — knowledge graphs, ontologies, rule engines, and formal logic. It is rigid, explicit, and fully auditable, but it cannot read a broker email or interpret a loss-run PDF on its own.

Neurosymbolic systems use the neural side to perceive — extracting structured facts from messy inputs — and the symbolic side to decide — applying your underwriting guidelines, regulatory requirements, and portfolio rules with deterministic precision. The neural model proposes. The symbolic engine disposes.

01 — NEURAL

Perceive

Extract entities, relationships, and intent from unstructured submissions — emails, ACORD forms, loss runs, inspection reports, news, geospatial imagery.

02 — ONTOLOGY

Represent

Map every extracted fact into a formal domain model: what a Risk is, what a Coverage is, how a Claim relates to a Peril and a Policy.

03 — SYMBOLIC

Reason

Apply underwriting guidelines, appetite gates, regulatory constraints, and capacity rules as executable logic — with every inference traceable to a rule and a fact.

04 — NEURAL (again)

Explain

Generate human-readable narratives, referral memos, and broker responses grounded in the reasoner's output — never hallucinated, always traceable.

02 / REASON

How the two systems actually think.

The difference isn't about accuracy on any single task — it's about the kind of cognition each system performs. An LLM generates the most plausible next token. A symbolic reasoner evaluates the truth value of propositions against a formal knowledge base. Understanding this gap is the key to knowing where to apply each.

Large Language Model

Statistical next-token prediction

"Based on what I've read, this pattern usually leads to that outcome."

  • MechanismTransformer architecture predicts the next token given the preceding context. Reasoning is an emergent side-effect of scale, not a guarantee.
  • KnowledgeImplicit. Compressed into billions of weights. Impossible to inspect, version, or selectively update without retraining.
  • ConsistencyProbabilistic. The same input can yield different outputs, especially at non-zero temperature.
  • TraceabilityNone. The model cannot cite which training example or which weight produced its conclusion.
  • StrengthUnstructured text, nuance, language fluency, summarization, and intent recognition.
  • WeaknessArithmetic, multi-step logic, rare edge cases, regulatory reasoning, hallucinations under ambiguity.
Neurosymbolic System

Logic over a knowledge graph

"Given these facts and these rules, this conclusion follows — here is the proof."

  • MechanismNeural extraction feeds an ontology; a reasoner applies first-order logic or rule systems (Datalog, OWL, RETE) to derive conclusions.
  • KnowledgeExplicit. Concepts, relationships, and rules live in a knowledge base you can read, version, and edit like source code.
  • ConsistencyDeterministic. Same facts plus same rules always produce the same conclusion. Reproducible across runs.
  • TraceabilityComplete. Every inference chains back to specific facts and named rules — a proof tree ready for audit.
  • StrengthPolicy compliance, capacity rules, multi-constraint optimization, portfolio accumulation, regulatory defense.
  • WeaknessBrittle on unstructured input without a neural front-end. Requires investment in ontology and rule authoring.
BUT WHAT ABOUT RAG?

"Isn't RAG the deterministic version of an LLM?"

The short answer is no — retrieval is deterministic, but generation still isn't. Retrieval-Augmented Generation pairs an LLM with a search engine over your documents. It grounds the model in your actual content, which dramatically reduces hallucination on factual questions. But the final answer is still produced by an LLM generating tokens. RAG improves an LLM; it doesn't turn an LLM into a reasoner. Here's how the three approaches handle the same underwriting submission.

LLM

Direct prompting

  • Submission → prompt
  • Transformer inference
  • Sample tokens
Output A fluent recommendation drawn from training-data patterns. Fast. Often plausible. No grounding in your specific rulebook.
RAG + LLM

Retrieval-augmented

  • Submission → query
  • Search underwriting docs
  • Inject top-k passages into prompt
  • Transformer inference
  • Sample tokens
Output A recommendation citing retrieved passages. Better grounded, but the model can still misread, paraphrase incorrectly, or ignore the retrieved text in favor of training-data priors.
NEUROSYMBOLIC

Ontology + reasoner

  • Submission → extract to ontology
  • Enrich across domains
  • Rule engine evaluates guidelines
  • Reasoner derives decision
  • Narrative generated from proof tree
Output A derivation — not a generation. Every conclusion chains to specific facts and named rules. Same inputs → same decision, always.
THE MYTH

"RAG makes LLMs deterministic."

The retrieval step is deterministic — the same query returns the same documents. But the generation step that uses those documents is still a probabilistic neural model, not a logical inference. Two runs can produce two different summaries, emphasize different clauses, or miss the same regulatory constraint.

THE REALITY

RAG improves factual grounding. It does not add reasoning.

An LLM reading a retrieved underwriting manual is still an LLM. It cannot guarantee that rule CP-ACC-02 fires every time the accumulation threshold is crossed. It cannot do multi-step constraint-satisfaction. It cannot emit a proof. RAG is a better LLM — NSAI is a different kind of system.

SYSTEM 1 · KAHNEMAN

Fast. Associative. Often right, sometimes dangerously wrong.

System 1 is pattern recognition at speed. It's the brain's autopilot — fluent, confident, and excellent for familiar problems. It's also where cognitive bias lives. When the pattern matches something common, System 1 is fast and accurate. When the situation is ambiguous, novel, or hinges on precise rules, it produces a confident answer that can be materially wrong.

A large language model is System 1 made mechanical — a pattern engine operating at machine scale, with machine confidence. RAG doesn't change the kind of thinking; it gives System 1 a better reference library. Faster recall, richer associations — but still not deliberation.
SYSTEM 2 · KAHNEMAN

Slow. Deliberate. Rule-following, multi-step, defensible.

System 2 is effortful thinking — the kind you use to apply regulations, work through a multi-step calculation, or weigh alternatives under constraints. It's slower and more expensive, but it's also the only kind of thinking that produces an auditable trail of why a decision was made. Underwriting is a System 2 discipline.

A neurosymbolic system operationalizes System 2 — and can apply several distinct modes of formal reasoning, the right one for the question.
REASONING MODES

Different questions demand different kinds of thinking.

Because a neurosymbolic system has an explicit model of the world, it can apply the reasoning mode that fits the question — not just probabilistic association. Each of these shows up somewhere in the underwriting pipeline. The rule engine does deductive work. Classifying a risk is abductive. Pricing involves causal reasoning. Structuring a placement is constraint-satisfaction. Stress-testing is counterfactual.

03 / ONTOLOGY

An ontology is a shared mental model — for machines.

Think of an ontology as the vocabulary and grammar of your business, written in a form a computer can reason over.

When an underwriter or actuary reasons about a risk — whether it's a commercial building, a group health policy, or a life annuity portfolio — they draw on a web of interconnected concepts. A risk has characteristics. Those characteristics relate to exposures, coverages, and rules. The human mind holds this web implicitly; an ontology makes it explicit and machine-readable.

An ontology names the classes (Policy, Party, Risk, Coverage, Claim), the properties (effective date, coverage limits, exposure amounts), and the relationships (a Policy covers a Risk, is issuedTo a Party, includes Coverage that settles Claims).

Without an ontology, the LLM knows the words. With an ontology, the system knows the meaning.

Once the world is modeled this way, rules become composable and inheritable. A rule that applies to "all combustible-construction buildings" automatically applies to anything the ontology classifies as combustible — frame, heavy timber, ordinary. You don't write the rule four times. You write it once, against the concept.

Most importantly, ontologies compose across domains. An activity ontology plugs into an exposure ontology plugs into a rating ontology. The same structure that supports underwriting supports claims, portfolio management, and regulatory reporting.

I.

Meaning, not matching

An LLM might see "whole life" and "permanent life insurance" as similar strings. An ontology knows they are the same concept — and knows exactly which reserve requirements, regulatory filings, and coverage rules attach to it.

II.

Rules follow concepts

A rule attached to HighRisk automatically applies to every subtype the ontology places under it — without re-authoring. Your guidelines become a small, maintainable hierarchy instead of a sprawling document.

III.

Cross-domain consistency

The same Activity decomposition anchors underwriting, claims, portfolio, and rating. One described job resolves to the same activity classes everywhere — the foundation of consistent pricing and meaningful claim-pattern comparison.

04 / REGULATORS

What regulators want — and why NSAI gives it to them.

Insurance regulators, state DOIs, NAIC working groups, and the EU AI Act don't care about model architecture. They care about three things: auditability, explainability, and bias. Each is harder to deliver with an LLM than with a neurosymbolic system.

I.

Auditability

Regulators increasingly ask carriers to produce, on demand, the exact reasoning behind an individual decision — why this risk was accepted, declined, or priced as it was. Not a narrative. A trace.

An LLM cannot produce this. A neurosymbolic system produces it by construction: the proof tree is the audit record. Every rule firing, every fact, every binding.

II.

Explainability

When a consumer asks why their claim was denied or their rate was high, carriers must be able to explain. Post-hoc LLM narratives are plausible text — they are not actual explanations of the model's internal state.

A neurosymbolic system's explanation is the reasoning. The narrative is generated from the proof, not fabricated alongside it. Same answer, every time, reconstructable years later.

III.

Bias & fairness

Regulators test for disparate impact across protected classes — race, ZIP code, gender, age. For an LLM, bias testing is statistical inference after the fact, and mitigation is retraining.

For a neurosymbolic system, the rulebook is the inspectable artifact. You can read every rule, test each one for bias, version-control changes, and prove a particular decision never used a forbidden attribute.

WITH AN LLM (or LLM + RAG)

Bias is a statistical property you test for

The model's biases live in billions of weights learned from training data. You cannot inspect which weight encodes which correlation. Mitigation requires adversarial probing, disparate-impact testing, and retraining.

  • Bias detection is post-hoc and probabilistic
  • Mitigation is slow, expensive, and incomplete
  • "Did this model use race?" is an empirical question
  • Regulatory defense requires a statistical argument
WITH A NEUROSYMBOLIC SYSTEM

Bias is a property of the rulebook you inspect

The knowledge base and rule set are explicit, readable artifacts. You can diff them like source code, test each rule in isolation, and prove — by construction — that a specific decision never consulted a forbidden attribute.

  • Bias detection is deterministic and direct
  • Mitigation is editing a rule and re-running
  • "Did this decision use race?" has a yes/no answer
  • Regulatory defense is a proof, not a statistic
